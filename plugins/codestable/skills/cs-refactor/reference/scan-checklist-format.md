# scan 清单格式

保留可追溯范围、候选和取舍。字段可按任务合并，不凑条数或方法编号。

```markdown
---
doc_type: refactor-scan
refactor: {YYYY-MM-DD}-{slug}
status: pending-user-selection | user-reviewed
scope: {文件/目录范围}
summary: {具体问题和建议范围}
---

# {slug} scan

## 总览
{范围、值得做的问题、风险及顺序；已授权的范围记录依据}

## 条目

### [编号] {具体动作}
- 位置：{文件:行号或符号}
- 现状与问题：{具体重复、职责冲突或性能证据}
- 建议：{改动及行为等价边界；方法编号仅在有帮助时引用}
- 风险与验证：{失败方式和对应证据；必须由用户完成才标 HUMAN}
- 范围：{模块/文件}
- 决定：{纳入/不做/待决定，依据或理由}
```

已有用户授权确定的范围可直接进入 design，记录依据并使用 `user-reviewed`，不伪造逐条审批。未决范围保持 `pending-user-selection`，只询问实质取舍。排除项保留理由。

解释实际维护或性能代价，不只写“更优雅”；性能收益需测量。按可理解和回滚边界组织条目，不设同一函数条数上限；可读性改进不必捏造数字指标。
